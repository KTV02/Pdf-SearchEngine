# Migrating an existing installation

Back up the complete existing installation, configuration, index data, PDFs, email state, cloud state, and Docker volumes before changing it. Keep that backup private. Do not replace or restart a working server until a separate test installation has passed.

1. Record the current effective Compose configuration and running image versions without sharing its output; it may contain credentials. Keep the existing `.env`, `docker-compose.override.yml`, `roles.json`, and `access_config.json` private.
2. Start from a clean copy of the shared source. Copy local values into its ignored `app/.env` and root `compose.override.yaml`. Point storage variables at the existing host directories. The defaults now use `app/data/`; they do not automatically pick up old paths. Carry over any custom network, capability, token mount, and image overrides explicitly.
3. Copy `access_config.json` to the private directory selected by `CONFIG_HOST_PATH` or mount its containing directory and set `ACCESS_CONFIG_PATH`. Keep `roles.json` and `role_indices.json` in the private backup for reference. Convert every legacy IP grant into an explicit entry for the person's Tailscale login. In the Admin interface, grant the corresponding index read and write permissions and grant admin only to the intended administrators. Existing valid login grants carry over. In a hand-edited file, use unique logins, JSON booleans for `admin`, and arrays of names for `read` and `write`. Correct malformed access settings on disk if the API reports that they are unavailable.
4. For shared access, set `LOCAL_SINGLE_USER_MODE=false`, configure `ADMIN_TAILSCALE_USERS`, and retain the exact allowed frontend origins. Send browser traffic through Tailscale Serve and keep the direct ports private. If Serve connects from a peer other than loopback or the Docker gateway, set `PDFSEARCH_TRUSTED_PROXY_IP` to that exact peer. Point cloud callback URLs to the API through Serve. Reconnect cloud accounts that need to move from an old IP owner to a registered login and select the new connection in the relevant index settings.
5. Preserve any coordinator token mount and network route. Set `MAIL_TOKEN` to the same private random value in the backend and mail processor before restoring mail jobs. The mail credential authorizes attachment uploads only. Keep the email config and mail state mounts. Scripts that used IP grants need an authenticated user path. Remove any installation `TEST_BYPASS_TOKEN`. Use `scripts/run_integration_tests.sh` for the isolated test stack.
6. In a separate environment with copies of the data, verify startup, permissions, searches, uploads, mail, cloud returns, and backups. Check the merged configuration privately with `docker compose config`. Schedule the host switch after testing the rollback.

Git ignore rules apply only to files that are not already tracked. A previously tracked secret stays in Git history even after deletion. Never make an old repository public merely because its latest files have been cleaned; inspect its entire reachable history and rotate any exposed credentials. A new public repository initialized from a reviewed snapshot avoids publishing the old commit history. Keep private history and backups access-controlled.

## Restoring and troubleshooting mail jobs

Keep `tasks.json` and the mailbox checkpoints in `MAIL_STATE_HOST_PATH` with the job configs in `EMAIL_CONFIG_HOST_PATH`. A restored monitor without a job checkpoint copies the cursor from a matching legacy `<mailbox>_uid.json` in the state directory and leaves that file available for other restored jobs. If several jobs used the same legacy cursor, they inherit the same starting UID and track progress independently from then on. A newly created monitor starts at the latest existing INBOX message. Use a full inbox import to backfill older mail.

The mail processor treats the backend's HTTP 202 as acceptance into its upload queue. Check the backend's job history for antivirus, document processing, and indexing results. A monitor saves acceptance after each part and advances the UID after handling all its parts. A lost HTTP response or a process exit before an acceptance is saved can leave the outcome uncertain and cause an upload to be submitted again. Full inbox imports keep their own cursors for each folder and date window.

For a stalled monitor, look up its task ID in `email_processor.log` under `LOG_STORAGE_HOST_PATH`. The log gives the checkpoint filename (`mail-*.json`), the pending UID and part when known, and the reason for retrying. The `last_part` field is the last handled position in the MIME parts of the pending UID, counting the message body when present. Permanent failures include unreadable MIME, oversized attachments, and file-specific backend rejections such as HTTP 400 with code `invalid_file`. Reports under `MAIL_STATE_HOST_PATH/mail-failures/` contain the UID, the part number or `null` for a message-level failure, and a fixed reason. Keep these files private.

- For an outage, authorization denial, or other unexpected backend response, restore connectivity and verify the shared `MAIL_TOKEN`, the target index, and its upload mode. The monitor retries with a wait that doubles from 10 seconds to a five-minute cap. After correcting a credential or config loaded at startup, recreate the affected service with the same job configs and state mounts.
- For a checkpoint or failure report write error, restore write access and free space while the processor is running so it can save pending updates before sending more attachments.
- For an invalid checkpoint or changed IMAP `UIDVALIDITY`, back up the mail state before intervening. Restore a valid checkpoint for the same job and mailbox UID namespace, or retire the old job and create a new monitor. Run a full inbox import if older mail from the mailbox needs indexing.
